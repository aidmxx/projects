# EXTREME PROGRAMMING

## Definition
Extreme programming is a set of values, principles, and practices for rapidly developing high-quality software that provides the highest value for the customer in the fastest way possible.
<ul>
<li>XP emphasizes team work and it happens in iteration cycles (typically last 1-3 weeks).
<li>Improves a project in 5 essential ways: communication, simplicity, feedback, respect, and courage.
<li>Matters: (1) Coding: we need the program to work; (2) Testing: we need to know what we have done; (3) Listening: learn what the problem is in the first place; (4) Designing: take what your program tells about how it wants and feed it back into the program.
</ul>

## Basic practices
<ol>
<li>Planning game: business and development work together to create the most valuable product as soon as possible.

Rule:
<ul>
<li>Business identifies the feature they want in the system, which is written out as a user story.
<li>Development estimates how much effort each story needs to take and how to distribute the effort within the team to achieve the deadline.
<li>Business decides the order of the user stories that need to be implemented and how often to release a production.
</ul>
<li>Small releases: start with the small essential features, then add a few features each time.
<li>System metaphor: provides an easy to remember naming convention
<li>Simple design: always use the simplest design to complete the task, focusing on meeting the specified requirements, as additional requirements will likely arise the next day.
<li>Continuous testing
<ul>
<li>Unit tests: automated tests by the developer, test functionality as they write it
<li>Acceptance/functional tests: specified by the customer, test the overall system
</ul>
<li>Refactoring: refactor out the code that is duplicated inside the program
<li>Pair programming: two programmers are involved to build all production code (the code will be reviewed as it is written) 
<li>Collective code ownership: each developer is expected to be able to work on any part of the code.
<li>Continuous integration: all changes are integrated into the code daily, and the tests should run 100% before and after integration.
<li>40-hour work week: programmers need to work based on the desired time–if overtime continues for a several days, it means something is wrong with the process.
<li>On-site customer: the development team has access to a real customer who will actually use the system.
<li>Coding standards: have the standards for the code structure.
</ol>

## User story
<ul>
<li>A narrative that a user tells from her/his own perspective (scenario/situation that the user finds)
<li>(1) Testable: write automatic tests to detect the presence of the story; (2) Progress: customer is willing to accept the story as aa sign of progress toward the goals; (3) Bite-sized: the story should be completable within the iteration; (4) Estimable: technical team must be able to guess how much time required to get the work done.
<li>Characterize use cases based on 4 questions: purpose, contents, plurality, and structure
<li>Engeneering task: thing that must be done to accomplish the user story.
</ul>

## Roles
<ol>
<li>Tracker: keep attention about what programmer doing and takes action if things seem to be going off track.
<li>Manager: organize meetings, and make sure everything documented to be passed to the tracker.
<li>Customer: writes user stories and specifies functional tests.
<li>Programmer: estimates stories and what should be done and how much it takes to achieve the goals.
<li>Coach: observe everything and make sure the project continues on track.
<li>Tester: implements and runs functional test.
<li>Doomsayer: trucks the project risks and warns the team about his/her discoveries.
</ol>
